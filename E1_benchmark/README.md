# E1 — 측정 정확도 벤치마크 (Measurement Accuracy Benchmark)

**목적**: KinetiQ가 산출하는 관절각·반복수·템포가 **알려진 참값 대비 얼마나 정확한지**를 인체 실험(IRB) 없이 정량화한다. IEEE Access급 논문의 핵심 실험이며, 타당성 보고서 §4.2의 E1에 해당한다.

**대상 시스템**: KinetiQ `ver7-D7.66` (`squat-app/index.html`) — D7.65에서 발견된 결함 2건 수정 후
**착수**: 2026-08-21

---

## 1. 설계 원칙

### 1.1 프로덕션 코드를 그대로 실행한다 (재구현 금지)

벤치마크가 `calcAngle()`·`detectPhase()`를 다시 구현하면, 검증되는 것은 **제품이 아니라 재구현본**이다. 심사자는 이를 정확히 지적한다.

따라서 `extract_core.cjs`가 `index.html`에서 측정 관련 함수의 **소스 텍스트를 그대로 추출**하여 `kinetiq_core.generated.js`를 생성한다. 각 함수는 SHA-256 해시와 원본 라인 범위가 기록되므로, 모든 벤치마크 결과의 출처가 감사 가능하고 `index.html` 변경 시 즉시 감지된다.

**그대로 추출되는 측정 체인 (13개 정의, 10,057 bytes)**

| 정의 | 역할 |
|---|---|
| `onPoseResults` | 프레임 진입점 — 가시측 선택(L/R), 어느 랜드마크가 어느 각도로 가는지의 배선 |
| `calcAngle` | 3점 관절각 (2D 벡터 내적) |
| `calcTrunk` | 몸통 수직 대비 기울기 (atan2) |
| `calcAsymmetry` | 좌우 관절각 비대칭 |
| `smooth` | EMA 시간 필터 (α = 0.3) |
| `detectPhase` | 반복 카운팅 4-state FSM |
| `completeRep` | 반복별 각도 집계 (min/max) |
| `repScore` | 가중 기술 점수 |
| `STANDARDS`, `BODY_ADJ`, `getStd`, `getACSM`, `dev` | 기준 범위 해석 |

**스텁 처리되는 것 (부수효과 전용)**: DOM 쓰기, 음성 큐, 사진 캡처, 렌더링. `harness_shim.js`가 제공하며, **어떤 분기 조건도 스텁 반환값에 의존하지 않는다**.

### 1.2 시간은 벽시계가 아니라 영상 시간이다

`detectPhase()`/`completeRep()`은 `Date.now()`로 템포를 계산한다. 오프라인 재생에서 벽시계를 쓰면 그 값은 **벤치마크 머신의 디코딩 속도**를 재게 되어 무의미하다. 따라서 shim은 영상 표시 타임스탬프로 구동되는 **가상 시계(virtual clock)**를 설치한다. 결과 메타데이터에 `clock: "virtual"`로 공개된다.

### 1.3 결정론적 재생

라이브 동작은 프레임 드롭에 좌우된다. 재생은 공급된 모든 프레임을 정확히 한 번씩 방문하므로 머신 간 **비트 재현 가능**하다 (`replay: "exhaustive"`). 프레임률 민감도는 `decimate()`로 별도 측정한다.

## 2. 3계층 오차 분해 (Error Decomposition)

E1의 핵심 방법론적 기여. 단일 숫자("MAE 5°")가 아니라, 오차가 **어디서 생기는지** 분해한다.

| Tier | 입력 | 참값 출처 | 격리되는 오차 | 상태 |
|---|---|---|---|---|
| **Tier 0** | 해석적 합성 랜드마크 | 구성에 의해 정확 (기계정밀도) | 앱 자체의 각도 수학 · EMA 필터 · FSM | ✅ **완료** |
| **Tier 1.5** | 실제 mocap 관절 → 시상면 투영 | 마커 모션캡처 (정확) | 앱 로직 × **실제 인체 동작** | ✅ **완료** (§5) |
| **Tier 2** | 실제 영상 → MediaPipe → 코어 | 데이터셋 공개 카메라 투영 | 전체 end-to-end 제품 오차 | ✅ **완료** (§8) |

Tier 0에서 오차가 0이면, Tier 2에서 관측되는 오차는 **전부 지각(perception) 단계에 귀속**된다고 말할 수 있다. 이 논증 구조가 심사 방어력을 만든다.

### Tier 0 참값의 정확성 근거

`synth_kinematics.js`는 골격을 **관절각으로부터** 순기구학으로 구성한다. 각 원위 분절은 근위 분절 방향을 지정된 내각만큼 회전시켜 배치하므로

```
angle(hip, knee, ankle) ≡ theta_knee    (구성에 의한 항등식)
```

가 각도 측정 코드와 **무관하게** 성립한다. 즉 앱의 `calcAngle()`은 자신이 만들지 않은 값과 대조된다. 몸통 기울기만 파생값이며 독립적인 atan2 공식으로 계산해 `derived: true`로 표시한다.

## 4. 발견된 결함 — 템포 측정 (T0.4)

> **한 줄 요약**: `descentTime`/`ascentTime`은 하강/상승 **국면의 지속시간이 아니라 중간 각도 구간의 통과 시간**을 잰다. 그 결과 모든 정상 템포가 점수 함수의 최대 감점 구간에 몰려, 템포 항목의 변별력이 완전히 소실된다.

### 근거

`detectPhase()`는 무릎각 < 145°(STAND−15)에서 하강 타이머를 시작하고 < 115°(BOTTOM_TH)에서 멈춘다. 175°→88° 전체 하강이 아니라 **145°→115° 구간**만 측정한다.

| 실제 하강 | 앱 보고 | 비율 |
|---|---|---|
| 1.0 s | 0.30 s | 30% |
| 2.0 s | 0.45 s | 23% |
| 3.0 s | 0.67 s | 22% |
| 4.0 s | 0.90 s | 23% |

보고값은 참값에 **대체로 비례**(비율 0.236 ± 0.029)하지만 압축된 척도이며, `completeRep()`의 `Math.max(.3, dt)` 하한 클램프가 추가로 작용한다.

### 결과: 점수 변별력 소실

`repScore()`의 하강 감점 구간은 `<1초 = 40점 감점(최대)`이다. 실제 1–4초의 모든 템포가 1초 미만으로 보고되므로 **감점이 항상 최대치로 포화**된다.

| | 실제 템포 1s→4s 범위에서 |
|---|---|
| 현재 점수 | **95점 고정** (변별력 0) |
| 참 템포로 채점 시 | 97 → 100 → 99 (정상 변별) |

평균 **4.17점**(최대 5점)의 부당 감점이 모든 사용자에게 발생한다.

### 하위 전파 (6개 소비처)

| 위치 | 영향 |
|---|---|
| `index.html:1077, 3328-3329` | 화면 "운동 속도 하강/상승 X초" 표시 |
| `index.html:3394` | `repScore()` 템포 감점 (가중 10% + 5%) |
| `index.html:3422` | 회차별 템포 표 색상 — 모든 반복이 빨강("너무 빠름") |

| `index.html:4249` | LLM 코칭 컨텍스트 → AI 코치가 "하강이 빠르다"고 조언 |
| `index.html:3865, 3974, 4230, 4422` | PDF 리포트 템포 섹션 |

### 조치

1. **수정 필요 (D8 후보)** — 하강 타이머를 국면 경계(움직임 시작 ~ 최저점)에서 시작·종료하도록 변경. 임계값 교차가 아니라 속도 부호 변화 또는 STAND 이탈 시점 기준.
2. **기존 데이터 처리** — 이미 내보낸 CSV의 `descent_s`/`ascent_s`는 **템포로 해석 불가**. 해당 컬럼을 사용한 분석이 있다면 무효.
3. **논문 서술** — 이 발견 자체가 E1의 가치를 입증하는 사례다. "합성 참값 하니스가 5,000명 시뮬레이션이 놓친 구성타당도 결함을 발견했다"는 서술은 방법론적 기여로 제시 가능하다. 단, **수정 후** 결과를 본 실험으로 보고하고 결함은 발견 사례로 인용하는 것이 정직한 구성이다.

## 5. Tier 1.5 결과 — 실제 인체 동작 (2026-08-21)

**Tier 1.5**는 Tier 0(합성)과 Tier 2(영상) 사이에 새로 정의한 계층이다. REHAB24-6의 **OptiTrack 마커 mocap을 MediaPipe 랜드마크 자리에 직접 투입**하여, 지각(perception)을 우회한 채 프로덕션 측정 체인을 실제 인체 동작으로 구동한다.

> 여기서 나오는 문제는 전부 **애플리케이션 로직**의 문제다. 포즈 추정 오차가 아니다. Tier 2 − Tier 1.5 차이가 곧 지각 기여분이다.

실행: `python3 harness/tier15_export.py … && node harness/tier15_run.cjs --in …`
대상: Ex6 스쿼트, 9개 녹화, **191개 주석 반복** (mocap 오류 제외)

### 5.1 관절각 정확도 — 우수

| 관절 | MAE | bias | RMSE | p95 | max |
|---|---|---|---|---|---|
| 무릎 (최저) | **1.14°** | +0.91° | 1.46° | 2.03° | 9.92° |
| 고관절 (최저) | **1.18°** | +0.84° | 1.68° | 2.08° | 12.70° |
| 몸통 (최대) | **0.46°** | −0.24° | 0.82° | 0.97° | 6.15° |

지각이 완벽할 때 앱의 각도 산출은 실제 인체 동작에서도 **약 1° 이내**로 정확하다. 잔차는 EMA 지연과 반복 구간 정의 차이에서 온다. 단안 투영항(2D−3D)은 평균 0.88°(sd 3.04°)로 스쿼트에서는 작다.

### 5.2 반복 카운팅 — 결함 발견

| 지표 | 값 |
|---|---|
| 주석 반복 | 191 |
| 검출 | 181 |
| 매칭 | 173 |
| **미검출** | **18 (재현율 0.906)** |
| 오검출 | 8 (정밀도 0.956) |

**미검출 18건은 전부 깊이 임계(115°)를 통과한 정당한 반복이다.** 그중 **10건은 반복 내 무릎 최대 신전이 160°에 도달하지 못했다.**

`detectPhase()`는 반복 완료 조건으로 `knee >= STAND(160°)` 복귀를 요구한다. 따라서 **정점에서 무릎을 완전히 펴지 않는 연속 긴장(constant-tension) 스타일로 수행하면 그 반복은 구조적으로 카운트될 수 없다.**

특정 개인에게 집중된다 — PM_126은 20회 중 6회(30%)가 정점 153–157°로 미카운트, PM_113은 18회 중 6회(33%). 반면 PM_022·PM_043·PM_105는 미검출 0. **즉 실패는 무작위가 아니라 개인의 동작 스타일에 결부된 체계적 실패다.** 어떤 사용자에게는 앱이 반복을 아예 세지 못한다.

> 주의: 초기 가설이었던 "피험자의 평균 신전각이 낮을수록 미검출이 많다"는 **기각되었다**(상관 −0.23). PM_113은 중앙 정점 174.9°로 높은데도 33% 미검출이다. 원인은 피험자 평균이 아니라 **개별 반복 단위의 정점 신전 부족**이다.

### 5.3 템포 결함 — 실제 인체 동작에서 재확인

| | 값 |
|---|---|
| 실제 하강 (참값) | 중앙값 **1.50 s** (범위 0.80–2.63) |
| 앱 보고 | 중앙값 **0.30 s** |
| **0.3초 클램프 바닥에 걸린 비율** | **98/173 (56.7%)** |

Tier 0의 합성 데이터 발견(§4)이 **실제 인체 동작에서 독립적으로 재확인**되었다. 실제 반복의 절반 이상이 `Math.max(.3, dt)` 하한에 그대로 눌려 있다.

### 5.4 점수 타당도 — 물리치료사 라벨 대비

| | n | 평균 점수 | sd |
|---|---|---|---|
| 정상 수행 | 116 | 85.70 | 7.44 |
| 오류 수행 | 57 | 80.47 | 7.44 |

**AUC = 0.698.** 점수가 전문가 판정을 어느 정도 변별하지만 강하지 않다. 방향은 옳다(정상 > 오류). 템포 항목이 포화되어 변별에 기여하지 못하는 상태에서 얻은 값이므로, **템포 결함 수정 후 재측정하면 개선될 여지가 있다** — 이는 수정의 효과를 정량적으로 보여줄 좋은 before/after 지표다.

### 5.5 하니스 자체에서 발견·수정한 오류 (방법론 기록)

Tier 1.5 구축 중 **하니스 쪽 오류 3건**을 발견하고 수정했다. 논문 방법 절에 기록할 가치가 있다.

| 오류 | 증상 | 수정 |
|---|---|---|
| 반복 단위 재생 | EMA가 동작 중간에서 초기화(180°)되어 유령 반복 생성 | **녹화 전체 연속 재생**으로 전환 (프로덕션 사용 방식과 일치) |
| 시상면 축을 시행 전체 평균으로 추정 | 녹화 중 피험자가 방향을 바꿔 축이 무의미해짐 → 좌우 다리 투영각이 32° 불일치 | **프레임별 ML 축**(15프레임 평활) |
| 좌우 visibility 동일(0.99) | `lVis > rVis`가 동률에서 false → 앱은 오른쪽 다리를 재는데 참값은 왼쪽 | 분석 측 visibility를 높여 앱 선택과 일치 |

수정 전 무릎 MAE는 13.17°(투영항과 상관 −0.93)였고, 수정 후 **1.14°**가 되었다. 세 오류 모두 앱이 아니라 하니스의 문제였다.

### 6.3 파라미터 선택 — dev/test 분리

3. **D7.66 이전에 내보낸 CSV의 `descent_s`/`ascent_s`는 여전히 템포로 해석 불가.**

## 7. 결함 3 — 종횡비 미보정 각도 (Tier 2에서 발견, **미수정**)

> **한 줄 요약**: 앱은 MediaPipe의 **정규화 좌표**(x/W, y/H)로 각도를 계산한다. W≠H이면 이 스케일링은 **비등방(anisotropic)**이라 각도를 보존하지 않는다. 즉 모든 관절각에 체계적·각도의존적 오차가 실린다.

### 근거

`calcAngle(a,b,c)`는 `p.x`, `p.y`를 그대로 쓴다. MediaPipe는 x를 폭으로, y를 높이로 나눠 정규화하므로, 4:3 영상에서는 세로 방향이 가로 대비 1.333배 늘어난 공간에서 각도가 계산된다. `onPoseResults`부터 `calcAngle`까지 종횡비 보정이 **없다**(코드 전수 확인).

실측 확인 (REHAB24-6 camera18, 1080×1920):

| | 값 |
|---|---|
| 앱 vs **앱 자신의 정규화 공간** 기준 | **0.88°** — 앱의 각도 수학 자체는 정확 |
| 앱 vs **실제 이미지 평면(픽셀)** 기준 | **−23.7°** — 이것이 종횡비 왜곡 |

즉 앱은 자기 규약에는 충실하지만, **그 규약이 해부학적 각도를 나타내지 않는다.**

### 크기 (해석적 계산)

프로덕션 카메라(`getUserMedia 1280×960`, 4:3) 기준:

| 실제 무릎각 | 앱 보고값 | 오차 |
|---|---|---|
| 120° | 127.6° | **+7.6°** |
| 100° | 103.2° | +3.2° |
| 90° | 90.0° | 0.0° |
| 80° | 76.8° | −3.2° |
| 60° | 52.4° | **−7.6°** |

90° 부근에서 0이고 양쪽으로 벌어지는 **각도의존적** 오차다. 세로 영상(9:16, 스마트폰 세로 촬영)에서는 −24°까지 커진다.

### 왜 지금까지 드러나지 않았는가

- Tier 0·Tier 1.5의 합성 랜드마크는 **등방(uniform) 정규화**로 만들어져 왜곡이 재현되지 않았다. 하니스가 의도치 않게 관대했던 것이다. **Tier 1.5의 무릎 MAE 1.05°는 등방 입력 조건에서만 유효하며, 실제 카메라의 프로덕션 오차를 대표하지 않는다.**
- 실제 카메라 영상을 통과시키는 Tier 2에서 비로소 드러났다.

### 함의

1. **미수정 상태다.** 수정은 간단하지만(각도 계산 전 x에 W/H를 곱하거나 픽셀 공간에서 계산), `STANDARDS`의 기준 각도 범위·점수 임계·규준이 모두 **왜곡된 값에 맞춰 튜닝되어 있을 가능성**이 있어 동반 재보정이 필요하다. 단독 수정은 오히려 점수 체계를 깨뜨릴 수 있다.
2. **IRB 검증연구(고니오미터 대조) 전에 반드시 해결해야 한다.** 이 상태로는 기준 측정도구와 체계적으로 어긋난다.
3. 논문에서는 이것을 **Tier 2가 Tier 0·1.5로는 원리적으로 발견할 수 없는 결함을 잡아낸 사례**로 제시할 수 있다 — 3계층 오차분해 설계의 정당성을 보여주는 증거다.

## 8. Tier 2 결과 — end-to-end 제품 정확도 (2026-08-21)

REHAB24-6 **camera18 영상 30,028 프레임**을 프로덕션과 **동일한 MediaPipe 빌드·동일 CDN·동일 옵션**(modelComplexity=2, smoothLandmarks, conf 0.6)으로 통과시킨 뒤 verbatim 프로덕션 코어에 투입했다. **MediaPipe 검출률 9개 녹화 전부 100%** (0 프레임 누락).

프레임은 ffmpeg로 사전 디코딩해 순서대로 공급했다. `<video>` 시크는 프레임당 50–100ms가 들어 5,000 프레임에서 지배적 비용이 되고, 사전 디코딩이 더 빠르면서 **모든 프레임을 정확히 한 번씩** 방문하므로 재현성도 높다.

### 8.1 핵심 설계 — 동일 기준, 두 조건

Tier 1.5는 시상면을 **우리가 추정**했지만, Tier 2는 데이터셋이 **공개한 카메라 투영**을 기준으로 쓴다. 여기에 대조군을 더해 2×2를 만든다.

| | `reference_2d` (실제 픽셀) | `reference_2d_appspace` (앱 좌표계) |
|---|---|---|
| **대조군** (camera18 mocap 관절 → 코어) | = **종횡비 왜곡** | ≈ 0 (하니스 건전성 확인) |
| **Tier 2** (영상 → MediaPipe → 코어) | = **end-to-end 제품 오차** | = **MediaPipe 지각 오차** |

### 8.2 오차 분해

| | 무릎 | 고관절 | 몸통 |
|---|---|---|---|
| 하니스 건전성 (대조군 vs 앱 좌표계) | **1.10°** | 1.07° | 0.50° |
| **종횡비 왜곡** (대조군 vs 픽셀) | **25.63°** (bias −25.63) | 25.19° | 14.24° |
| **MediaPipe 지각 오차** (Tier 2 vs 앱 좌표계) | **17.62°** (bias +17.06) | 8.71° | 5.60° |
| **end-to-end 제품 오차** (Tier 2 vs 픽셀) | **14.02°** | 21.52° | 16.64° |

하니스 건전성 1.10°는 Tier 1.5의 ~1°와 일치 — 설계가 건전함을 확인한다.

> **주의**: 무릎의 end-to-end(14.02°)가 종횡비 왜곡 단독(25.63°)보다 **작다**. 이는 개선이 아니라 **두 오차의 부호가 반대(−25.6 vs +17.1)라 우연히 상쇄된 것**이다. 상쇄에 의존하는 정확도는 조건이 바뀌면 즉시 무너지므로 강점으로 해석해서는 안 된다.

### 8.3 반복 카운팅

| 조건 | 재현율 | 정밀도 |
|---|---|---|
| 대조군 (완벽 지각, 왜곡된 좌표계) | **0.707** | 0.938 |
| **Tier 2** (실제 지각) | **0.901** | 0.966 |
| (참고) Tier 1.5 등방 좌표계 | 0.984 | 0.959 |

대조군 재현율이 0.707로 급락한 것은 **종횡비 왜곡이 각도만이 아니라 반복 카운팅까지 망가뜨린다**는 뜻이다.

기제를 처음에는 "기립 175°가 ~150°로 읽혀 FSM의 STAND(160°) 조건을 놓친다"고 적었으나 이는
**틀렸다**. 비등방 정규화는 픽셀 공간을 x축으로 `k = H/W` 배 하는 것과 동치이고, 그 아래에서
참값 175°는 코퍼스 기하(1080×1920, k=1.778)에서 [171.1°, 177.2°], 4:3(k=0.75)에서
[173.3°, 176.3°] 범위로만 읽힌다. 150°에 닿으려면 k ≈ 6.1, STAND 게이트 160°를 뚫으려면
k ≈ 4.0 이 필요하다 — 실제 기하에서는 일어날 수 없다. 대조군 프레임 실측도 같은 결론이다:
기준 무릎 ≥173°인 10,404 프레임에서 앱 공간 판독의 최솟값은 167.6°로, STAND 게이트를
한 번도 벗어나지 않는다.

재현율 하락은 STAND 조건이 아니라 **굴곡 구간의 게이트**에서 온다. 비등방 왜곡은 두 분절이
거의 일직선일 때 가장 약하고 직각에 가까울 때 가장 강하다. 같은 k=1.778 에서 참값별 판독
범위는 다음과 같다.

| 참값 | 판독 범위 | 폭 |
|---|---|---|
| 175° | 171.1 – 177.2° | 6.1° |
| 160° | 145.2 – 168.7° | 23.5° |
| 120° | 88.5 – 144.0° | 55.5° |
| 90° | 58.7 – 121.3° | **62.6°** |

기립(175°)의 흔들림 폭은 6.1°에 그치지만 스쿼트 바닥 근방(90°)은 62.6°로 **10.3배**이고,
판독 범위 58.7–121.3°는 BOTTOM·PARALLEL 게이트를 통째로 가로지른다. 즉 왜곡이 깨뜨리는
것은 기립 판정이 아니라 하강 깊이 판정이며, 이는 Tier 2 무릎 bias −8.46°가 굴곡 구간에
몰린다는 관측과도 일관된다.

### 8.4 뷰 층화

| 뷰 | n | 무릎 MAE | bias |
|---|---|---|---|
| sagittal | 97 | 14.09° | −14.09° |
| oblique (half-profile) | 75 | 13.93° | +2.58° |

크기는 비슷하나 **bias 방향이 다르다**. sagittal은 일관되게 과소평가, oblique는 편향이 작지만 산포가 크다(p95 30.9° vs 23.7°).

### 8.5 점수 타당도

정상 82.24 (n=112) vs 오류 77.25 (n=60), **AUC 0.627**. Tier 1.5(0.711)보다 낮다 — 지각 오차가 변별력을 깎는다.

### 8.6 한계 (반드시 함께 보고할 것)

1. **팔다리 선택이 미관측이다.** 앱은 MediaPipe visibility로 좌/우를 고르는데, 이번 실행에서 landmark를 보존하지 않아 앱의 실제 선택을 관측하지 못했다. **일치도가 좋은 쪽을 사후 선택**했으므로 보고된 Tier 2 각도 오차는 **하한(lower bound)**이다. 좌/우 차이가 평균 18.3°(최대 36.1°)로 크므로 이 선택은 결과를 실질적으로 바꾼다. 프레임별 선택 팔다리를 기록하는 재실행이 필요하다.
2. **9:16 세로 영상이라 종횡비 왜곡이 프로덕션보다 크다.** 프로덕션 카메라는 4:3이며 그 경우 왜곡은 ±8° 범위다(§7). 이 데이터셋의 25°는 상한에 가깝다.
3. Tier 2는 **이 데이터셋·이 촬영 조건**에 대한 벤치마크이지 임상 타당도 연구가 아니다.

## 9. 종횡비 결함 수정 결과 (ver7-D7.67, 2026-08-21)

§8이 발견한 최대 오차원을 수정하고 **동일 코퍼스로 재검증**했다. MediaPipe는 다시 돌리지 않았다 — §8.6의 한계를 해소하려 landmark 30,028 프레임을 전부 영구 저장했고(`tier2_corpus/`, 40MB), 이후 모든 실험은 오프라인 재생으로 수초 만에 끝난다.

### 9.1 이전 한계 2건 해소

1. **팔다리 선택 미관측 → 해결.** 앱의 선택은 visibility의 순수 함수(`lm[11,23,25,27]` vs `lm[12,24,26,28]` 평균)이므로 landmark만 있으면 정확히 복원된다. **9개 녹화 전부 `left`**(안정도 94–100%)였다. §8에서 일치도 기준으로 사후 선택한 `right`는 **전부 틀렸다**. 따라서 §8이 보고한 무릎 오차 14.02°는 무효이며 **실제 값은 32.73°** 였다 — 하한값 caveat이 그만큼 컸다.
2. **오프라인 재생 가능 → 해결.** 조건 A/B/C 비교, 임계 스윕, dev/test 검증이 모두 재실행 없이 수행됐다.

### 9.2 세 조건 비교 (191 반복)

### 9.3 최종 — 프로덕션 코드 end-to-end

하니스가 좌표를 미리 스케일하지 않고 **프레임 기하만 제시**하면, 보정은 프로덕션 코드가 직접 수행한다. 그래야 하니스가 아니라 제품을 측정한다.

**핵심 수치는 시상면 5.63°다.** 앱이 안내하는 측면 촬영에서의 무릎 오차이며, 전체 15.16°는 사면 반복(27.66°)이 끌어올린 값이다.

### 9.4 회귀 게이트가 잡아낸 것

깊이 게이트를 135로 올리자 D7.66에서 추가한 되돌림 가드(`_ascentPeak >= BOTTOM_TH+25`)가 160(=STAND)이 되어 **D7.66의 카운팅 수정이 통째로 무력화**됐다. Tier 1.5 재현율이 0.984→0.916으로 떨어져 발견했고, 가드를 `STAND-20`으로 분리해 복구했다(0.979). **측정 로직을 만질 때 전 계층을 회귀 게이트로 돌려야 하는 이유다.**

### 9.5 남은 것

- **사면 뷰 27.66°** — 이미지 평면 보정으로는 복구 불가능한 3D→2D 투영 손실. 단안 카메라의 원리적 한계이며, **측면 정렬 촬영 안내 UX가 정확도에 직접 기여**한다는 정량 근거.
- 상승 시간 약 25% 과소 측정 (D7.66부터 미해결).
- **STS 모듈 미적용** — 별도 파이프라인이라 동일 결함 가능성이 높으나 E1으로 검증되지 않았다.
- Tier 2는 이 데이터셋·이 촬영 조건 벤치마크이지 임상 타당도 연구가 아니다.

## 12. 주장 위생 (Claim Hygiene) — 반드시 지킬 것

Tier 0은 **소프트웨어 정확성 실험이지 측정 타당도 연구가 아니다.** 참값이 알려진 입력에 대해 소프트웨어가 무엇을 하는지 확립할 뿐, KinetiQ가 **인체를 정확히 측정한다는 근거가 되지 못한다.**

- Tier 0 결과를 "측정 타당도 검증"으로 서술하지 말 것.
- 인체 측정 정확도는 Tier 2(모션캡처 참값) 또는 IRB 검증연구(N≈30)에서만 주장 가능.
- 기존 `SIMULATION_LOG.md`의 5,000명 시뮬레이션과 동일한 원칙 — 그것은 데이터 무결성 검증이었고, 이것은 측정 체인 정확성 검증이다.

## 14. 외적 타당도 — 두 번째 모캡 코호트 UI-PRMD (2026-08-22, 엔진 ver7-D7.85)

### 14.3 해석

1. **체인 항이 재현된다.** 2D 기준 bias +1.53° — REHAB 의 +1.05° 와 같은 부호·같은 자릿수이고, 전 피험자에서 0.65–2.78° 로 균일하다. T0.2 가 합성 입력에서 정량화한 **EMA 깊이 과소평가**(최저점을 실제보다 덜 굴곡으로 읽음)가 세 번째 독립 입력(합성 → OptiTrack → Vicon)에서도 같은 크기로 나타난 것이다. 이것이 §14 가 답하려던 질문의 답이다.
2. **3D 기준 오차의 피험자 의존성은 체인이 아니라 투영 항이다.** 위 표에서 체인 항은 0.65–2.78° 범위(폭 2.1°)에 머물지만 투영 항은 −4.7° ~ +7.1°(폭 11.7°)다. s10 의 8.57° 는 체인 1.49° + 투영 7.08°. 투영 항은 앱 출력과 무관하게 기준값끼리의 차이(2D−3D)로 계산된 것이므로 **시상면 밖 성분**(무릎 외반·발 회전 등)의 크기이며, 이미지 평면 계산으로는 원리적으로 복구 불가능한 단안의 하한이다. §9.5 의 "사면 뷰 27.66°" 와 같은 종류의 항이 정면 정렬 상태에서도 피험자에 따라 수 도 남는다는 뜻이다.
3. **카운팅은 게이트가 적용되는 범위에서 사실상 완벽하다.** 미검출 8회 중 7회는 2D 최저 무릎 136–163° 로 **깊이 게이트(135°) 위** — 카운트 대상이 아니도록 설계된 영역이다(§9.2 의 게이트 재도출 참조). 나머지 1회(s07 e07)는 134.1° 로 게이트 경계, EMA 평활 후 135° 에 못 미쳤다. 게이트 이하 191 세그먼트 중 190 검출, FP 0.
4. **점수 AUC 0.571 은 결함도 타당성 증거도 아닌 구성개념 불일치다.** `repScore` 는 최저 무릎각이 `STANDARDS.bodyweight.knee = [80, 100]`(패럴렐 깊이 규범) 안에 있는지로 채점한다. UI-PRMD 의 correct 딥스쿼트는 3D 최저 무릎 중앙 **74°** 로 규범보다 깊어 감점(평균 88.1점)되고, 모사된 incorrect 는 중앙 **92°** 로 규범 안이라 비슷하게 점수(85.2)가 나온다. 라벨은 "딥스쿼트로서 올바른가", 점수는 "패럴렐 규범에 맞는가"를 묻는다 — 이 코호트에서 두 질문의 답은 반대다. REHAB(0.716) 과 차이 나는 이유는 두 데이터셋의 '정상' 정의가 다르기 때문이며, 이 결과는 점수 구성개념의 **경계**를 표시한다는 점에서 보고 가치가 있다. 원고에는 "reported, not claimed" 로 쓴다.
5. correct 의 MAE(4.15°) 가 incorrect(2.79°) 보다 큰 것은 깊은 굴곡에서 투영 항이 커지는 경향(2D−3D 와 GT3D 무릎의 Pearson r=0.18, n=190, 리포트 `projection_floor_deg.pearson_r_vs_gt3d_knee`; 약함)과 s10·s09 의 correct 가 깊은 쪽에 몰린 효과다. 체인 항은 두 군에서 차이가 없다.

### 14.4 범위 — 반드시 함께 보고할 것

- **T1.5 다.** MediaPipe 인지 오차는 **포함되지 않는다**. 이 숫자는 "측정 체인 + 투영 기하"의 숫자이지 end-to-end 제품 정확도가 아니다. UI-PRMD 에 영상이 없으므로 Tier 2 는 원리적으로 불가능하다 — 인지 오차는 여전히 REHAB24-6 한 데이터셋에서만 측정됐다.
- 고관절 중심은 ASI/PSI 중점 **근사**다 (회귀식 관절 중심이 아님). 측면 각도 목적으로는 표준적이지만 고관절 수치는 이 근사를 안고 있다. REHAB 의 26-관절 골격과 관절 중심 정의가 달라서 투영 하한의 차이(0.22° vs 0.66°)에 기여했을 수 있고, 이는 분리 불가능하다.
- **REHAB 대조값은 같은 코드로 만든 것이 아니다.** REHAB T1.5 열(`tier15_matched.csv`)은 `tier15_export.py` 의 투영(`rehab24_6.project_to_sagittal`, 등방 정규화, 프레임 기하 미지정)이고, UI-PRMD 는 `yaw_sweep` 투영(yaw 0°, 1280×960)이다. 스윕이 yaw 0° 에서 T1.5 를 0.01° 안에서 재현하므로(무릎 MAE 2.41° vs 2.42°, bias 1.91° vs 1.92°, recall/precision/AUC 동일) 비교는 성립하지만, 표에는 두 값을 나란히 적는다. 고관절 3D 대조는 T1.5 CSV 에 없어 스윕 yaw 0° 값(3.25°)을 쓴다.
- 건강한 성인이 **모사한** 오류 수행이다. 임상 표본이 아니다.
- 시상면은 골반축에서 추정한 가상 카메라다. 실제 카메라 배치가 아니다.
- 벤치마크이지 임상 타당도 연구가 아니다 (§12).

### 14.5 하니스 자체에서 발견·수정한 것 (방법론 기록, §5.5 의 연장)

첫 실행은 191/200 매칭, **FP 1, 고관절 오차 94.2° 이상치 1건**이었다. 추적 결과 셋 다 **같은 원인** — 데이터셋 분할 오류 — 였고, 세 번의 시도 끝에 올바른 처리에 도달했다. 기록해 둘 가치가 있는 경로다.

| 단계 | 조치 | 결과 | 판정 |
|---|---|---|---|
| 0 | 파일 사이 홀드 = 항상 마지막 프레임 | s07 e04(1.13 s, 무릎 113° 에서 종료)의 최저점 프레임이 홀드되고 다음 파일의 기립 프레임으로 점프 → FSM 이 가짜 상승을 봄 → e04 이벤트가 e05 창에 매칭(고관절 173° vs 참 79°), 진짜 e05 검출은 FP | 하니스 아티팩트 |

| 2 | 비기립 경계로 이어진 두 파일을 한 에피소드로 병합 | 병합 구간에서 앱이 **반복 2회** 검출 → 첫 이벤트(무릎 113°, 고관절 174°)가 매칭되고 둘째가 FP. 고관절 94.7° 잔존 | 참값이 틀렸다는 신호 |

교훈 세 가지. (i) **"FP" 가 참값 오류일 수 있다** — 이벤트 시각과 원시 궤적까지 내려가 확인하기 전에는 앱 탓도 하니스 탓도 하지 말 것. (ii) 배제는 **앱 출력과 무관한 기준**으로만 한다 — 그래야 "오차가 큰 것을 뺐다"는 의심을 받지 않는다. R1/R2 는 3D 참값 궤적만 본다. (iii) 데이터 수술(홀드 바꾸기, 병합)은 증상을 옮길 뿐이다 — 증상이 옮겨 다니면 원인은 더 위에 있다.

첫 실행 → 최종의 지표 변화: 무릎 MAE 3D 3.53→3.51°, 2D 1.56→1.53°, 고관절 MAE 3.02→2.54°(이상치 제거), recall 0.955→0.960, precision 0.995→1.000, AUC 0.574→0.571. **체인 항·투영 항의 결론은 처음부터 같았다** — 아티팩트가 바꾼 것은 고관절 이상치와 FP 뿐이다.
